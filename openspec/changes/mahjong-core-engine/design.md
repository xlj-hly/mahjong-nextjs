## Context

项目是 Next.js 16 脚手架（`src/app` 仅默认首页），已配好 ESLint/oxfmt/commitlint/husky，无测试框架。本 change 是纯 TS 库 + 前端热座，不引入网络或服务端依赖。动机见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**

- 立起「规则无关核心 + 规则插件接口」的边界，使第二种规则（四川/日麻）可增量接入而不改核心。
- 国标 81 番种 + 不重复原则正确落地，并以单元测试覆盖。
- 热座模式跑通一整局，验证引擎与规则插件。

**Non-Goals:**

- 不实现实时对战/WebSocket/房间/断线重连（第三层）。
- 不实现 AI 托管/陪打。
- 不实现观战、回放、战绩持久化。
- 不实现第二种规则插件（第二层）。

## Decisions

### D1: 牌张编码

用不可变对象表示单张牌：`{ suit, rank }`，其中 `suit` 为 `'wan' | 'tong' | 'tiao' | 'wind' | 'dragon' | 'flower'`，`rank` 为数牌 1–9、风牌 1–4（东南西北）、箭牌 1–3（中发白）、花牌 1–8（春夏秋冬梅兰竹菊）。花牌作为独立 suit，避免污染数牌逻辑。

- 备选：纯数字编码（如 0–143）。**否决**——可读性差、易错，且不同规则牌种集合不同，对象更清晰。
- 备选：花牌单独一个数组不放入手牌。**部分采纳**——手牌模型里花牌单独存放，见 D3。

### D2: 手牌结构

手牌表示为「已排好序的牌列表（不含花牌）+ 花牌列表 + 副露（吃/碰/明杠/暗杠）列表」。和牌判定仅对「牌列表 + 副露」进行，花牌单独计番。

- 理由：花牌不参与面子拆解，单独存放可简化拆解与番种算法。

### D3: 面子拆解算法（规则无关，核心）

对一副 14 张（或补副露后）手牌，用递归回溯枚举所有「4 面子 + 1 对将」拆解：先枚举对将候选（出现 ≥2 的牌），再对剩余牌依次尝试刻子/顺子，剪枝后返回所有互异拆解。特殊牌型（七对、十三幺、全不靠等）由规则插件在拆解之外单独判定。

- 备选：DP / 图论建模。**否决**——回溯实现直白、易测，且牌数固定小（14），性能无压力。
- 该算法是规则无关的，供所有插件复用。

### D4: 规则插件接口（`RulesPlugin`）

接口包含：`id`、`tileSet`（牌种集合构建牌墙）、动作合法性（`canChow/canPong/canKong/canWin`）、`isWinningHand(hand, ctx) → WinningInfo | null`（和牌判定 + 番数）、`calcScore(...)`（结算）、`flow`（补花/定缺/流局等钩子）。引擎核心只依赖该接口，不 import 任何具体规则。

- 备选：把和牌判定也放进核心。**否决**——特殊牌型与番种高度规则相关，放插件才守得住边界。

### D5: 番种判定与不重复原则

番种判定拆两层：

1. **特征提取**：从拆解出的每种面子组合，提取结构特征（是否清一色、是否碰碰和、是否门前清、各刻子/顺子情况、听牌方式等）。
2. **番种匹配**：81 番种各自定义匹配谓词，返回命中的番种集合与番值。
   不重复原则通过「番种互斥组」实现：维护互斥关系（如清一色/混一色、全带五/全带幺等），从命中的番种中按组只保留番值最高者，再累加。国标官方「不重复原则」有标准互斥表，本 change 以该表为准落地。

- 关键风险：互斥表不全会导致番数算错，见 Risks。

### D6: 热座模式

对局推进逻辑放在纯 TS 的 headless 运行器里（不依赖 React），React 侧通过 `useHotseatGame` 状态容器持有该运行器实例，只做「消费 snapshot 展示」与「上报意图」两件事。UI 按当前行动方位展示对应玩家手牌，其余玩家手牌隐藏。判定全在引擎。

- 理由：对局推进放纯 TS（可测），React 只做展示与意图上报，二者分离，为后续 WebSocket 复用引擎铺路。

### D7: 测试框架

选用 **Vitest**（与项目现有的 ESM/`"type": "module"`/Turbopack 生态一致，配置轻）。引擎与规则插件逻辑全部纯函数，单测覆盖拆解算法、和牌判定、番种计算、不重复原则、结算。

- 备选：Jest——ESM 配置较重。**否决**。

### D8: 目录结构

```
src/
  game/                  # 纯 TS 库（引擎核心 + 规则插件，与框架无关）
    core/                # 牌张/牌墙/拆解/状态机骨架/插件接口
    rules/               # 规则插件
      guobiao/           # 国标插件（tileSet、和牌、番种、互斥表、结算）
  app/                   # Next.js 页面（热座 UI 入口）
  components/            # 热座 UI 组件
```

`src/game` 不 import 任何 `next`/React，保证引擎可被独立测试与后续服务端复用。

### D9: 表现层边界与快照/意图契约

UI 与引擎之间只通过两个口子交互，使渲染器（2D DOM / three.js / CLI）可整体替换：

1. **只读快照**：UI 通过 `engine.snapshot(seat)` 获取当前局面（手牌、牌河、副露、花牌、当前行动方、该座玩家的 `legalActions`）。快照是纯数据、不可变；UI 不得触及引擎的可变内部状态。
2. **上报意图**：UI 只通过 `engine.apply({ seat, action, tile })` 上报玩家意图（出/吃/碰/杠/和）。合法性判定、和牌与番数计算全部由引擎完成，组件内禁止重复实现。

表现层自身分三层接缝，逐层可替换：

- **牌数据**（稳定，永不改变）：引擎的 `Tile` 对象（`suit + rank`）贯穿 UI props。
- **牌视觉 `TileView`**（同一渲染范式内可换）：单张牌怎么画——v1 用汉字 + CSS 牌块外壳。
- **棋盘视图 `BoardView`**（可整体换）：桌面/手牌/牌河的布局与交互，是 2D DOM 与 three.js 3D 的替换点。

交互方式（DOM `onClick` vs Raycaster）是 `BoardView` 的内部细节，但「我要打这张牌」的**意图是稳定类型**，与交互方式解耦。

- 备选：组件直接读引擎内部数组并自行判断合法性。**否决**——会把 81 番种/状态机逻辑复制进 UI，3D 迁移时推倒重来。
- 试金石：提供一个不依赖 React 的 **headless 对局运行器**，能纯命令行跑完整一局；2D/3D/CLI 都只是它的客户端，同时作为规则端到端测试资产。

## Risks / Trade-offs

- [81 番种「不重复原则」互斥表不完整 → 番数算错] → 以国标官方规则互斥表为唯一依据，逐番种写单测，含互斥边界用例；对 88/64 大番种重点加测。
- [拆解算法遗漏或重复拆解 → 番种判定错误] → 回溯返回互异拆解，单测覆盖「多解」「无解」「特殊牌型」三类。
- [花牌单独存放后，补花/亮花与手牌张数一致性易错] → 状态机中花牌与手牌分离管理，单测覆盖连续补花与牌墙耗尽。
- [插件接口抽象过松或过紧 → 第二种规则接入时被迫改核心] → 以「国标 vs 四川/日麻」的已知差异（花牌有无、字牌有无、定缺/振听）反向验证接口够用；接口先最小化，不预设计未用字段。

## Migration Plan

无——从零新增，无存量数据或接口需迁移。新增测试与代码不影响既有 `src/app` 脚手架（或将首页改为热座入口，见 Open Questions）。
